# Non-functional requirements: evidence

Traceability: `TASK-NFR-01` to `TASK-NFR-30`, `docs/PRD/NFR-CATALOG.md`. Written 2026-10-03, after the business modules were built. The foundation tasks (`docs/TASK/PHASE-0-FOUNDATION.md`) delivered the machinery; this page says, requirement by requirement, what shows that it holds today, what was measured, and what is **not** proven and needs a person or a real environment. Nothing here is a promise about the hotel's own server: the measurements were taken in the build sandbox (a PHP development server with 16 workers and MySQL 8 on a shared machine), which is a floor, not the Niagahoster plan.

Status words: **Evidenced** (the requirement is met as far as it can be shown without the real environment), **Evidenced, with open items** (met in part; the open items are listed and owned), **Not met** (a known gap with an owner decision).

## What was measured in this pass

| What | How | Result |
| --- | --- | --- |
| Time to a usable page on a phone (NFR-01) | `npm run audit:browser -- perf`: Chromium, 390 px wide, signed in, nothing cached, network shaped by Lighthouse's *Slow 4G* (1.6 Mbit/s, 150 ms) and by *Fast 4G* (9 Mbit/s, 170 ms); gzip and the one-year cache of `/build/assets` as in `public/.htaccess` | Fast 4G, first visit: every page 1.5 s (279 kB on the wire). Slow 4G, first visit: every page 2.9 s (312 to 347 kB), the dashboard 2.85 s. Second visit: 0.3 to 0.5 s (nothing but the page data is fetched) |
| The same without compression and caching (the first run) | the PHP development server as it is | 929 to 1,119 kB and 5.7 to 6.7 s on Slow 4G, which is why `public/.htaccess` now compresses and caches |
| Server time and queries of the busiest pages on a house of 150 rooms (NFR-01) | `tests/Integration/Foundation/PerformanceBudgetTest.php`: 150 rooms, 60 bookings, 30 guests in the house | Room board 16 queries and 0.019 s; housekeeping board 19 and 0.019 s; stays 11 and 0.014 s; reservations 12 and 0.015 s; dashboard 90 and 0.057 s. No page makes more queries on 150 rooms than on 3 |
| 5,000 POS bills in the day (NFR-02) | `tests/Feature/FnbSales/PosCapacityTest.php`: a real settled bill copied to 5,000 (bill, lines, batch, payment, revenue row), all in one cashier shift | POS floor 0.012 s; cashier shift 0.058 s; revenue 0.018 s; menu report 0.057 s; dashboard 0.179 s; one more bill opened, ordered, sent and paid 0.127 s |
| 50 users at the same time (NFR-02) | `npm run audit:load -- --property=<id> --users=50 --seconds=30`: 50 signed-in sessions opening the busiest pages at the pace of a person | 1,087 requests, 0 errors, 36 requests a second; page time p50 0.50 s, p95 1.08 s, p99 1.44 s |

| Every page opens without an error (found by the same browser) | `npm run audit:browser -- crawl --pages=auto` | 162 pages: no script error, no failed request. It found one real defect (see below) |

### Defects found while collecting this evidence, and fixed

1. **Finance pages crashed on a hotel with no documents yet.** The payables, the payables ageing, the receivables and the receivables ageing pages formatted zero in an empty currency (`Invalid currency code`) until the first invoice existed. The currency is now the property's own. Test: `tests/Feature/Foundation/GuideAndEmptyStateTest.php`.
2. **A property that has not gone live had a server error (500) on every page that needs the business date.** It is now an expected 409 with the words "Set it under Property settings when the hotel goes live" in both languages.
3. **The room board made one query for every room** (165 queries for 150 rooms). A block check is now one query for all rooms.
4. **The list of guests in the house made 3 queries for every guest** (98 queries for 30 guests): the guest, the room and the permission were read again for each. They are read once.
5. **An Indonesian reader downloaded two dictionaries before the first paint** (the language chosen and the English fallback, 318 kB before compression). The fallback is now fetched after the first paint; the dictionary tests keep both languages on the same keys, so it is only a safety net.
6. **No compression and no caching headers** in `public/.htaccess`. The text types are compressed; `/build/assets` (named by the hash of their content) is kept for a year; pages are never cached.

## How to repeat the measurements

```
npm run build
php artisan serve                                  # or the real server
npm run audit:browser -- perf  --base=<url> --email=<user> --password=<password>          # --profile=fast for 9 Mbit/s
npm run audit:browser -- a11y  --base=<url> --email=<user> --password=<password> --pages=auto
npm run audit:browser -- crawl --base=<url> --email=<user> --password=<password> --pages=auto
npm run audit:load -- --base=<url> --property=<property id> --users=50 --seconds=30      # needs one account per user, `load{n}@...`
vendor/bin/phpunit tests/Integration/Foundation/PerformanceBudgetTest.php tests/Feature/FnbSales/PosCapacityTest.php
```

`scripts/browser-audit.mjs` needs Playwright, which is not a dependency of the project: the global installation is used when there is one. Against a server that is not behind Apache or LiteSpeed it puts a small proxy in front that compresses and caches as `public/.htaccess` does (`--prod-like=false` turns that off).

## Dependency added

`axe-core` 4.13 (development only, MPL-2.0, no dependencies) runs the accessibility rules of `NFR-27` in the browser audit. It is not part of the production build and is not loaded by any page. Rationale: an accessibility claim without an automated rule engine is an opinion; writing the WCAG rules by hand would be worse.
